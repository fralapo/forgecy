# 0015 · A client package is untrusted input: nothing arrives approved

- Status: accepted
- Date: 2026-10-08
- Amends: 0009 (import behaviour)

## Context

ADR 0009 imports a package by generating new ids and keeping every other value. The package is written by whoever made it: statuses and "who approved" are as free to choose as ids and storage keys. The audit found that a crafted package could arrive with content already Approved or Exported, with approvals attributed to real local people (people are matched by email, which the package states), with published templates (including `origin: system`), with the AI consent of the client already given, with automations active and with Brand Identity versions already published. Each of these skips a gate that `can()` enforces for everything created here.

The structural checks (every foreign key and `client_id` stays inside the package, storage keys are this client's, files match their checksum) keep a package from reaching into another client. They do not say what a row may claim, which is this decision.

## Decision

The importer applies `applyImportTrust` (`packages/client-transfer/src/trust.ts`) to every row, after the final scope check and before the insert, on the remapped parsed rows. The rules are per table:

Template reuse during import looks only at agency templates (`client_id is null`) and, for a replacement, the replaced client's own templates; another client's private template is never mapped in. Verify and Import decide with the same function (`templateReuse` in `templates.ts`), for a new client, so a conflict is offered exactly where the import honours the choice. Templates are unique by key and version across the installation, so a package template whose version is held by a template that cannot be reused is imported as `<version>-import.<n>`, a valid semver prerelease (`compareVersions` in `@forgecy/carousel` orders it just below the release), with `manifest.version` of the row following. Every row that names a template by key and version follows a rename or a reuse (`rewriteTemplateRefs`): the `template_key`/`template_version` columns and the same pair inside any JSON, including `content_versions.meta.templateVersion` (which export prefers over the column) and the pipeline's `{ template, version }`. A test builds one row of each shape and checks that none still names the old version. Export and preview resolve a template by key and version without looking at the client, so a stale reference would have rendered with another client's private template. Copying a client inside one installation, or importing a package twice, therefore works.

### Rules fail closed

`checkTrustCoverage` checks the rules against the Drizzle schema. It runs in a unit test and before every import (not when the module loads, so a schema change cannot take export or verify down). It finds the gate columns by name (status, decision, approved/published/exported, accepted, confirmed, acknowledged, resolved, rights, shares and tokens, public, enabled, locks, waivers, reviewers, submitters, deciders) and by value (any enum that has one of `approved`, `published`, `accepted`, `exported`, `active`, `confirmed`, `verified`, whatever the column is called). Then: every client table with such a column, or an export/approval table, needs a rule; every value of a status enum needs a target that is a value of the enum; every gate column has to be named by the rule (cleared, set, or listed as deliberately left); a rule may only clear nullable columns; a rule that changes nothing states why. Every JSON column must also be in `REVIEWED_JSON_COLUMNS`, the list of columns that were read for approvals embedded in them (a person's name, `accepted`, `confirmed`, `verified`); the ones that held one have rules (listed above). A new table, a new status value, a new approval column or a new JSON column therefore stops the importer until someone decides what it means, as `SOFT_REFS` does for references. A status value this version does not know is refused at import (`UnsafePackageError`).

### A status change must not break a unique index

Mapping statuses changes which rows fall inside a partial unique index, and the package is only known to satisfy the index as it was. The first version mapped `delivered` audits to `in_review`; a client with a delivered audit and a reviewed one then had two active audits (`audits_one_active_uq`) and the import failed. Rule: a mapping may move a row out of such an index, never into it. `STATUS_UNIQUE_INDEXES` lists the status-dependent unique indexes of the client tables (`audits_one_active_uq`, `brand_versions_one_published_uq`, `brand_versions_one_open_uq`, `content_plans_active_uq`); a test checks every mapping against them and fails for any partial unique index of the schema that is in neither that list nor `NOT_STATUS_DEPENDENT`. Check constraints that tie a status to an approver (`brand_proposals_reviewed_by_person`, `content_creative_directions_decided_by_person`, `brand_versions_*_by_person`) are why proposals and directions leave `accepted`/`rejected` and why an approved version leaves `approved` before its approver is cleared.

No package signature: a hash or HMAC proves origin only between installations that share a secret. The checks make an untrusted package harmless instead. A signature can be added later without changing the format (a new manifest field).

## Consequences

A package from a trusted source arrives needing the same clicks it needed on the source (submit, approve, publish, re-enable automations, re-approve the AI providers and rights), and its templates must be published again. A delivered audit arrives archived. This is intended.

A new client from a package never gets more AI freedom than a client created by hand: the installation's default policy caps it (the default is read with the same fallback as `getDefaultAiPolicy`, `resolveDefaultAiPolicy` in core), and no provider is approved. The default policy and a replaced client's consent are read again inside the import transaction, with the replaced client locked, so a change made while the rows were prepared is not overwritten. The import wizard describes the reset (`clientTransfer.confirm.states`).

Export records are not imported and their files are not copied. What is deliberately not reset: product data keeps its status and field `truth` levels (only the acceptance of sensitive claims is removed, and such a product must be approved again), strategy and competitor status travels, `product_images.status`, the `verdict` of brand examples, `memory_items.confidence` (a package could forge `high` to make a memory eligible for bulk approval; the memory is still a candidate that a person approves), `ReportSection.byAgent`, `product_import_files.valid`, and proposals' suggested values (a proposal that sets a font license to `verified` is still accepted by a person). None of these unlocks an export or sends anything.
