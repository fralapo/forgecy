# 0015 · A client package is untrusted input: its approvals are not imported

- Status: accepted
- Date: 2026-10-08
- Amends: 0009 (import behaviour)

## Context

ADR 0009 imports a package by generating new ids and keeping every other value. The package is written by whoever made it: statuses and "who approved" are as free to choose as ids and storage keys. The audit found that a crafted package could arrive with content already Approved or Exported, with approvals attributed to real local people (people are matched by email, which the package states), with published templates (including `origin: system`), with the AI consent of the client already given, with automations active and with Brand Identity versions already published. Each of these skips a gate that `can()` enforces for everything created here.

The structural checks (every foreign key and `client_id` stays inside the package, storage keys are this client's, files match their checksum) keep a package from reaching into another client. They do not say what a row may claim, which is this decision.

## Decision

The importer applies `applyImportTrust` (`packages/client-transfer/src/trust.ts`) to every row, after the final scope check and before the insert, on the remapped parsed rows. The rules are per table:

Template reuse during import looks only at agency templates (`client_id is null`) and, for a replacement, the replaced client's own templates; another client's private template is never mapped in. Verify and Import decide with the same function (`templateReuse` in `templates.ts`), for a new client, so a conflict is offered exactly where the import honours the choice. Templates are unique by key and version across the installation, so a package template whose version is held by a template that cannot be reused is imported as `<base>-import.<n>` with the smallest free n (a version that already ends in `-import.<n>` keeps its base, so a template exported and imported again never grows: at most `x.y.z-import.999`, and the export and render caps on the version are 32 characters) (`planTemplateImport` reserves the names it hands out, so two templates of the package never end up with one), a valid semver prerelease (`compareVersions` in `@forgecy/carousel` orders it just below the release) (the row only: the stored `manifest` keeps the version of the package, which the strict x.y.z rule requires). Every row that names a template by key and version follows a rename or a reuse (`rewriteTemplateRefs`): the `template_key`/`template_version` columns and the same pair inside any JSON, including `content_versions.meta.templateVersion` (which export prefers over the column) and the pipeline's `{ template, version }`. A test builds one row of each shape and checks that none still names the old version. Templates are looked up by key and version, so a reference left pointing at an old version would have been served by whichever template holds that version; lookups are therefore scoped to the client (see "A template is only served to its own client"). Copying a client inside one installation, or importing a package twice, therefore works.

### Rules fail closed

`checkTrustCoverage` checks the rules against the Drizzle schema. It runs in a unit test and before every import (not when the module loads, so a schema change cannot take export or verify down). It finds the gate columns by name (status, decision, approved/published/exported, accepted, confirmed, acknowledged, resolved, rights, shares and tokens, public, enabled, locks, waivers, reviewers, submitters, deciders) and by value (any enum that has one of `approved`, `published`, `accepted`, `exported`, `active`, `confirmed`, `verified`, whatever the column is called). Then: every client table with such a column, or an export/approval table, needs a rule; every value of a status enum needs a target that is a value of the enum; every gate column has to be named by the rule (cleared, set, or listed as deliberately left); a rule may only clear nullable columns; a rule that changes nothing states why. Every JSON column must also be in `REVIEWED_JSON_COLUMNS`, the list of columns that were read for approvals embedded in them (a person's name, `accepted`, `confirmed`, `verified`); the ones that held one have rules (listed above). A new table, a new status value, a new approval column or a new JSON column therefore stops the importer until someone decides what it means, as `SOFT_REFS` does for references. A status value this version does not know is refused at import (`UnsafePackageError`).

### A template is only served to its own client

A row that names a template by key and version can name one the package does not carry. Export, preview and the Brand Book resolve a template by key and version, and `dbTemplateSource` did so without looking at the client, so such a reference would have rendered with whatever template holds that version here, possibly another client's private one; an export without a pinned version took the newest published version across all clients. `dbTemplateSource` now takes the client (`clientId: string | null`, required) and serves agency templates and that client's own only (`templatesVisibleTo`); every caller passes it (the export job, the preview route, `/render/slide`, the Brand Book job, the audit report export). The Brand Book pins the newest version the client may use (`newestVisibleVersion`), not the newest of all clients, so one client's private Brand Book template cannot make the others' renders fail. The content module's `getTemplate` and `listUsableTemplates` already did.

Closed by `docs/adr/0021-private-client-templates.md`: it makes this the rule for every template lookup, lists them, and fixes the three places this section did not reach (an agency upload replacing a client's private draft, a deleted prospect's templates becoming agency ones, a template's versions listed across owners).

### Ordering by `created_at`

Rows keep the `created_at` the package gives them. Where the newest row decides a gate, a forged date wins: that was `brand_check_runs` (dropped, above). The other `orderBy(desc(createdAt))` selections read for display or analysis (audit scans and sources, assets, comments, proposals, examples, product imports and field proposals) or pick a version by its number (content, brand and report versions); none gates an approval or an export. A new gate that reads "the latest row" must not use a date the package can set.

### A status change must not break a unique index

Mapping statuses changes which rows fall inside a partial unique index, and the package is only known to satisfy the index as it was. The first version mapped `delivered` audits to `in_review`; a client with a delivered audit and a reviewed one then had two active audits (`audits_one_active_uq`) and the import failed. Rule: a mapping may move a row out of such an index, never into it. `STATUS_UNIQUE_INDEXES` lists the status-dependent unique indexes of the client tables (`audits_one_active_uq`, `brand_versions_one_published_uq`, `brand_versions_one_open_uq`, `content_plans_active_uq`); a test checks every mapping against them and fails for any partial unique index of the schema that is in neither that list nor `NOT_STATUS_DEPENDENT`. Check constraints that tie a status to an approver (`brand_proposals_reviewed_by_person`, `content_creative_directions_decided_by_person`, `brand_versions_*_by_person`) are why proposals and directions leave `accepted`/`rejected` and why an approved version leaves `approved` before its approver is cleared.

No package signature: a hash or HMAC proves origin only between installations that share a secret. The checks make an untrusted package harmless instead. A signature can be added later without changing the format (a new manifest field).

## Consequences

A package from a trusted source arrives needing the same clicks it needed on the source (submit, approve, publish, re-enable automations, re-approve the AI providers and rights), and its templates must be published again. A delivered audit arrives archived. This is intended.

A new client from a package never gets more AI freedom than a client created by hand: the installation's default policy caps it (the default is read with the same fallback as `getDefaultAiPolicy`, `resolveDefaultAiPolicy` in core), and no provider is approved. The default policy and a replaced client's consent are read again inside the import transaction, with the replaced client locked, so a change made while the rows were prepared is not overwritten. The import wizard describes the reset (`clientTransfer.confirm.states`).

Export records are not imported and their files are not copied. What is deliberately not reset: strategy and competitor status travels, `product_images.status`, the `verdict` of brand examples, `memory_items.confidence` (a package could forge `high` to make a memory eligible for bulk approval; the memory is still a candidate that a person approves), `ReportSection.byAgent`, `product_import_files.valid`, `product_imports.closed_by` (who closed an import), `contents.product_revision` (the catalog revision a carousel was written against: a forged value can only hide that the product changed, which the person approving still sees), and proposals' suggested values (a proposal that sets a font license to `verified` is still accepted by a person). None of these unlocks an export or sends anything. Known limitation, not new: a proposal authored by a person (`author_type = user`) whose author is not present here has its `author_user_id` emptied, which violates the `brand_proposals_author` check; the import then fails with that raw database constraint error, rolls back and writes nothing. Remove or re-author such proposals in the source before exporting.
