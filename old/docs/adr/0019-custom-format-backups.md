# 0019 · New backups are custom-format dumps, restored with pg_restore

- Status: accepted
- Date: 2026-10-09
- Amends: 0018 (how a restricted restore leaves out the extension)

## Context

A backup held its database as plain SQL (`db.sql`, `pg_dump --clean --if-exists --no-owner`), loaded with `psql -X --single-transaction -v ON_ERROR_STOP=1`. psql runs backslash meta-commands wherever its lexer sees them: `\!` runs a shell command on the worker, `\copy` and `\i` read local files. pg_dump itself now writes `\restrict`/`\unrestrict` lines into plain dumps because a hostile server could inject meta-commands into one (CVE-2025-8714). Forgecy refuses meta-commands with a scanner (`packages/backup/src/safe-dump.ts`) that follows psql's lexer (quotes, dollar quotes, comments, COPY data); any gap between that model and psql is code execution on the worker. `docs/SECURITY_CHECKLIST.md` (section 7) left "restore through `pg_dump -Fc` and `pg_restore`" open.

pg_restore sends an archive's SQL to the server through libpq. There is no psql on that path, so meta-commands do not exist there. The statements in the archive still run as the restoring role.

## Decision

- New backups (Settings, nightly, pre-restore, pre-import, `pnpm forgecy backup`) hold `db.dump`, written by `pg_dump --format=custom`. The manifest says `"format": 2, "db": "custom"`. `BACKUP_FORMAT` becomes 2 because an older Forgecy checks only `format === 1`: it then reports "This backup uses a format this version doesn't know" at inspection and refuses the upload. With format 1 it would have accepted the backup and failed only during the restore, after the pre-restore backup, on a missing `db.sql`. Old versions have no allowlist of archive entry names to fall back on.
- Backups of format 1 (no `db` field, `db.sql`) restore exactly as before: scanner, then psql.
- `backupDbFormat` (`packages/backup/src/archive.ts`) reads the manifest. Format 1 with no `db` (or `"plain"`) is plain SQL. Format 2 with `"custom"` is a custom dump. Anything else is refused: `format` at inspection, `BACKUP-INVALID` at upload, an error at restore. `extractedDump` then requires the file the manifest names and refuses an archive that also holds the other one, so the manifest can only pick one of two fixed names. Worker, web upload and CLI share both functions.
- Custom restore: `pg_restore --clean --if-exists --no-owner [--use-list <list>] --single-transaction --exit-on-error --dbname <url> db.dump` (`pgRestoreArgs`). The first three options do at restore time what they did at dump time for plain backups. The last two give the same guarantees as psql's `--single-transaction` and `ON_ERROR_STOP=1`: one transaction, stop at the first error, nothing changed on failure.
- Before that, the scanner reads the archive's SQL. `pg_restore` renders the same `db.dump` file with the same options and list to a file (`--file`, no connection), and `assertSafeDumpFile` reads it in chunks. If the scanner refuses it, pg_restore never connects. The rendering leaves out only `--single-transaction`, which would just add the `BEGIN`/`COMMIT` the scanner refuses. pg_restore 17.10 writes `\restrict`/`\unrestrict` lines into the rendering (checked), and the scanner already accepts them at the start of a line (`PG_DUMP_META`). On this path they are never executed.
- Restricted restore (ADR 0018): `pg_restore --list db.dump`, without the `EXTENSION - <name>` entries (they carry both the DROP and the CREATE under `--clean`) and the `COMMENT - EXTENSION <name>` ones (`withoutExtensionEntries`). The resulting list is passed with `--use-list` to both the rendering and the restore. Leaving entries out can never add one. The ownership step is unchanged.
- Worker: `pgRestoreInto` runs the local `pg_restore`. The worker image already installs `postgresql-client-17`, which ships pg_restore with pg_dump and psql, so the Dockerfile does not change. The web image only stores uploads and reads manifests. CLI (`scripts/lib/backup.ts`): the same steps. With Compose running, the tools run inside the postgres container and the archive and list are copied with `docker compose cp` into a private folder in its `/tmp`, removed afterwards. Without Compose, the host's tools (17+) run, or the `pgvector/pgvector:pg17` image with the files mounted read-only.

## Consequences

- New backups no longer go through psql, so the scanner's model of psql's lexer protects only plain backups made before this decision.
- Still unprotected, as before: the archive's statements run as the restoring role. A crafted custom archive can carry any SQL, as a plain dump could. The scanner still reads every statement, with the residual of ADR 0018: SQL built at run time (a `DO` block running `EXECUTE`) passes it. Run as the `DATABASE_URL` superuser, such SQL can run programs, read server files or create roles during the restore. The optional restore role of ADR 0018 is the defence for that. Triggers or functions planted for later still run as the superuser later. Restore only backups you made or trust.
- The scanner is stricter than pg_restore needs. A genuine database with an object whose rendering it refuses is refused: for example a table name containing a quote or `;` (its `COPY` header), or a `BEGIN ATOMIC` function. Forgecy's schema has none; report such a refusal as a scanner bug, as for plain backups.
- A restore writes a temporary SQL rendering about the size of the old `db.sql`. pg_restore reads the archive twice, three times in a restricted restore. Through Compose the CLI copies the archive into the container for each of those reads.
- A Forgecy older than this ADR cannot restore a custom backup. `pnpm forgecy upgrade` takes its backup with the new code, so to go back to an older version, restore that backup before downgrading, or by hand: extract `db.dump` and run the `pg_restore` line above.
- Proven by `packages/backup/test/custom-format.integration.test.ts` and `restore-role.integration.test.ts` (they run with `FORGECY_TEST_DATABASE_URL` and psql, pg_dump and pg_restore 17+ on PATH, otherwise skipped). A real custom dump of the migrated schema round-trips through `restoreArchive`. An archive whose rendering the scanner refuses (a table named `x) TO PROGRAM 'id'; --`) fails before pg_restore is called, and the target database stays unchanged. A plain backup still restores with psql. A custom backup restores as the restricted role, after failing first without the ownership step and without the filtered list, with the database unchanged after each failure. Unit tests cover the manifest rules (`archive.test.ts`, `restore.test.ts`). The CLI was checked by hand in its three modes: Compose, host tools, and the pgvector image.
